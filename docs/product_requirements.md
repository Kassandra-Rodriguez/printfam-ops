# Product Requirements — PrintFam Ops

## 1. Problem statement

PrintFam's customer requests and orders arrive through eight uncoordinated channels (Instagram DM, text, Shopify, TikTok Shop, email, phone, in-person, and returning-customer word of mouth). Nothing ties a conversation to an order, a proof to an approval, or a payment to a balance. The result: forgotten orders, lost details, missed follow-ups, un-tracked approvals, and unclear balances owed.

PrintFam Ops is a single operational system of record for every customer, request, order, proof, repair, payment, file, message, task, and deadline — built first for internal use at PrintFam, architected from day one to become a multi-tenant SaaS product for other small businesses.

## 2. Goals

**Business goals**
- Stop losing orders and follow-ups across fragmented channels.
- Make "what needs my attention right now" answerable in under 5 seconds.
- Get PrintFam's current active orders into the system on day one, without waiting for any external integration.
- Build on a foundation that can be sold to other small businesses without a rewrite.

**Product goals**
- Manual data entry must be fast, forgiving, and support entering work already mid-progress (not just new work starting at step one).
- Every workflow (request, custom order, existing-product order, repair, quote, proof) is explicit and status-driven, not ad hoc.
- The interface is built for a daily-use, non-technical small-business owner — not an enterprise CRM administrator.

## 3. Non-goals (explicitly out of scope for v1)

- Automatic ingestion from Instagram, TikTok Shop, Shopify, email, or SMS. Manual entry only; integration *interfaces* are prepared, not built.
- Online payment processing (Stripe collection). Payments are recorded manually.
- Advanced reporting/BI beyond the basic report list in the source spec.
- Multiple locations, multiple warehouses, or advanced inventory (transfers, purchase orders).
- Custom per-organization status editing UI (the data model supports it from day one; the settings UI to edit statuses ships in Phase 8).
- Native mobile app (responsive web only).

## 4. Primary user (v1) and future users

- **v1 primary user**: PrintFam's owner (Kassandra), operating essentially as Owner + Manager + Team Member simultaneously.
- **v1 secondary user**: PrintFam customers, via a read-mostly portal (proof/quote approval, payment status).
- **Future users**: other small businesses and larger organizations as tenants, each with their own Owner/Manager/Team Member/Customer roles. See `user_roles.md`.

## 5. Guiding product principle

Every screen decision is filtered through one question: **does this help answer "what needs my attention right now?"** Decorative metrics, empty dashboards, and enterprise-CRM configuration screens are deprioritized in favor of an actionable, urgency-ranked, always-current view of open work.

## 6. Core entity glossary

| Entity | Definition |
|---|---|
| Customer | A person or company PrintFam has interacted with. One profile, deduplicated across channels. |
| Request | An inquiry, lead, question, or possible job — not yet committed work. |
| Order | Committed work the business has agreed to complete: custom, existing-product, bulk, or service. |
| Repair Ticket | A distinct workflow for diagnosing and repairing a customer's device — separate from Order because its fields (intake, diagnostics, parts, warranty) don't fit the order shape. |
| Quote | A priced proposal, optionally tied to a Request, that can be approved and converted into an Order. |
| Proof | A versioned visual/file artifact requiring customer approval before production proceeds. |
| Payment | A manually recorded amount against an Order, Quote deposit, or Repair balance. |
| Task | A follow-up or to-do linked to any of the above. |
| Communication | A logged message/call/conversation from any channel, linked to a Customer and optionally a Request/Order/Repair. |
| Activity Log | An immutable audit trail entry generated by significant actions across the system. |

## 7. Functional requirements by module

### 7.1 Customers
- Create/edit a customer with contact info across channels (phone, email, Instagram, TikTok, Shopify customer ID), preferred contact method, notes, tags.
- Duplicate detection on phone, email, Instagram handle, TikTok handle, Shopify ID at creation time (warn, don't block).
- Profile aggregates: requests, orders (active/completed), repairs, spend, outstanding balance, files, communications, activity.

### 7.2 Requests
- Full request lifecycle per the statuses in §9.
- Convert-to-order action that **preserves** customer, messages, notes, files, quotes, tasks, activity history, and source information (no data loss, no re-entry).

### 7.3 Orders (custom, existing-product, bulk, service)
- Manual creation in **Quick Entry** (customer, title, type, status, total, due date, notes) and **Detailed Entry** (every field: items, pricing, deposit, dates, files, notes, tasks, communication history, source).
- **Critical requirement**: status is selectable at creation time — an order can be entered already "in production," "waiting for final payment," etc. Historical dates, existing payment history, and progress notes must be enterable retroactively.
- Draft support so incomplete entries aren't lost.
- Table, board, and calendar views.

### 7.4 Repair tickets
- Full intake → diagnostic → approval → parts → repair → testing → completion → pickup lifecycle per §9.
- Same manual-entry and mid-workflow-entry requirement as orders.

### 7.5 Quotes
- Line items, labor, materials, discounts, tax, shipping, deposit, expiration, terms, notes.
- Status lifecycle per §9. Convertible to an order without data loss.

### 7.6 Proofs
- Multi-version upload (image/PDF/design file), customer-facing message, internal-only vs customer-visible flag, secure approval link (no customer account required), approval/revision recording with timestamp and required revision comments, full version history retained.
- Configurable gate: production cannot proceed while `approval_required = true` and no approved version exists.

### 7.7 Payments
- Manual recording only in v1: amount, method, date, deposit/final flag, reference number, notes, receipt attachment.
- Methods: cash, Cash App, Zelle, card, Shopify, TikTok Shop, Square, bank transfer, other.

### 7.8 Tasks
- Linked to customer, request, order, repair, proof, or quote. Title, description, assignee, due date, priority, status, reminder, completion date.
- System-suggested tasks on key events (quote sent, proof stalled, order ready, part needed, balance due, pickup overdue, request unanswered) — suggestions are created as real, editable/dismissible task records, never fake/inert UI.

### 7.9 Communications
- Manually logged messages/calls per channel (Instagram, text, TikTok Shop, Shopify, email, phone, in person, other), with direction, timestamp, content, attachments, linked request/order, recorder, follow-up flag/date.
- Paste-to-log quick entry. Create customer/request/order directly from a communication. Generate a follow-up task from a communication.

### 7.10 Files
- Attachable to customer, request, order, repair, message, quote, proof, product. Name, type, uploader, date, visibility (internal/customer-visible), description.

### 7.11 Inventory
- Product catalog (name, description, category, images, SKU, price, cost, available/reserved qty, reorder level, active flag, customization options, production notes).
- Inventory transactions logged on configurable order-status triggers (e.g., decrement on "in production," release reservation on cancellation).

### 7.12 Activity history
- Every significant state change creates an immutable, queryable activity log entry (see `data_model.md`).

### 7.13 Search & filtering
- Global search across customers, orders, requests, repairs, notes, tracking numbers.
- Per-module filters: type, status, source, assignee, due date, payment status, proof status, pickup status, priority, tags.

### 7.14 Notifications
- In-app notifications for the event list in the source spec (new request, task due/overdue, quote/proof approved, revision requested, message received, payment recorded, deadline approaching, repair approval received).

### 7.15 Reports (Phase 8)
- Revenue by month, orders by type, requests by source, conversion rate, AOV, outstanding balances, average completion time, overdue orders, popular products, repair/custom revenue split, completed/cancelled counts, repeat customers.

### 7.16 Roles & multi-tenancy
- Owner, Manager, Team Member, Customer roles (see `user_roles.md`).
- Every record scoped to an `organization_id`; strict tenant isolation enforced at the database (RLS) and application layers.

### 7.17 Customer portal
- Token-based (no full account required) view of order/quote/proof status, approve/decline actions, file upload, payment status, messaging, pickup/shipping info, repair approval — with strict exclusion of internal-only data (see `security.md`).

## 8. The manual-entry & mid-workflow requirement (do not deprioritize)

This is the requirement that unblocks PrintFam's actual day-one usage and therefore governs build sequencing:

1. Every entity in §6 must be manually creatable before any external integration exists.
2. Orders and repairs must be creatable **at any status**, not just the first step, with backdated timestamps, pre-existing payment history, notes, and files attached at creation.
3. Quick Entry must never block on fields that aren't known yet; Detailed Entry captures everything once available.
4. Drafts must never be silently lost.

Phase 3 of `build_phases.md` exists specifically to satisfy this requirement end-to-end before any other module is built.

## 9. Status vocabularies (authoritative for v1 seed data)

These are the **default** status sets seeded per organization at creation. They are stored as data (`workflow_statuses`), not hardcoded UI strings — see `data_model.md` §"Workflow configuration" — so a future tenant can rename/reorder them without a code change, even though the v1 UI to edit them ships in Phase 8.

- **Request**: New → Reviewing → Waiting for Customer → Quote Needed → Quote Sent → Follow Up Needed → Approved → Converted to Order → Declined → Lost → Archived
- **Custom order**: Request Received → Gathering Details → Quote Needed → Quote Sent → Waiting for Deposit → Design in Progress → Proof Sent → Revision Requested → Customer Approved → Production Queued → In Production → Quality Check → Waiting for Final Payment → Ready for Pickup → Ready to Ship → Shipped → Completed → Cancelled
- **Existing-product order**: Order Received → Payment Pending → Paid → Preparing Order → Ready for Pickup → Ready to Ship → Shipped → Completed → Cancelled
- **Repair ticket**: Repair Requested → Awaiting Drop Off → Device Received → Diagnostic in Progress → Waiting for Customer Approval → Waiting for Parts → Repair in Progress → Testing → Repair Completed → Waiting for Payment → Ready for Pickup → Returned to Customer → Closed → Cancelled
- **Quote**: Draft → Sent → Viewed → Approved → Declined → Expired → Converted to Order

## 10. Assumptions & product decisions

These are decisions made to keep scope shippable; flagged explicitly per the instruction to document assumptions rather than pause for confirmation.

1. **Repairs are a separate entity (`repair_tickets`), not an order sub-type.** Their fields and lifecycle diverge too far from `orders` to share a table cleanly. They appear alongside orders in the single "+ New" creation menu for UX consistency.
2. **Bulk order** is treated as `orders.order_type = 'bulk'` and, at creation, the user picks whether it needs production (reuses the custom-order status list) or is stock-only (reuses the existing-product status list) via a `requires_production` flag. This avoids inventing a fourth, undocumented status vocabulary while still surfacing "Bulk Order" as its own clear menu choice.
3. **General service order** gets its own lightweight status list, since the source spec didn't define one: Requested → Scheduled → In Progress → Waiting for Payment → Completed → Cancelled.
4. **Linking design**: attachments, messages, and tasks use explicit nullable foreign keys (`customer_id`, plus one of `request_id` / `order_id` / `repair_ticket_id` / `quote_id` / `proof_id`) rather than a polymorphic `(type, id)` pair. This preserves referential integrity and keeps Postgres RLS policies simple (see `data_model.md`, `architecture.md`).
5. **Statuses are config-driven data, not enums baked into the UI**, from day one — required by the "no hardcoded statuses" coding standard and by the multi-tenant goal, even though the *editing* UI for custom statuses is deferred to Phase 8.
6. **No payment processing, no live integrations in v1** — confirmed explicitly in the source spec; the app must be fully usable without them.
7. **Single location/warehouse assumed for v1 inventory.** Multi-location is a documented future extension, not built now.
8. **Customer portal accounts are not required.** Access is via scoped, expiring tokens per record, matching the "no full account" requirement while leaving room for optional customer login in a later phase.

## 11. MVP acceptance criteria

The MVP (end of Phase 3 for entry, full list by end of Phase 7 per `build_phases.md`) is done when:

- [ ] A user can sign up, create an organization, and invite/assign roles.
- [ ] A user can create a customer, and duplicate-detection surfaces on matching identifiers.
- [ ] A user can create every one of the 12 manual record types listed in the source spec (customer, request, custom order, existing-product order, repair, quote, payment, task, communication note, proof, inventory adjustment, partially-completed order).
- [ ] An order or repair can be created directly into any valid mid-workflow status, with backdated history, existing payments, and notes attached — with no forced pass through earlier statuses.
- [ ] Quick Entry produces a valid order with 7 fields in under 60 seconds; Detailed Entry exposes every field; an in-progress entry survives a page reload as a draft.
- [ ] The dashboard's attention list (not charts) is the first thing rendered, is accurate against live data, and every row opens or updates its record without full navigation.
- [ ] A quote can be sent, approved by a customer through the portal (no account), and converted to an order without losing linked records.
- [ ] A proof can be uploaded, versioned, sent, and approved/revision-requested through the portal, and a production-blocking gate respects `approval_required`.
- [ ] A payment can be recorded against an order/quote/repair and the balance updates everywhere it's displayed.
- [ ] All of PrintFam's current active orders (seed data, §`build_phases.md`) can be represented without a workaround.
- [ ] No record is ever visible to a second organization created in the same database (verified by an automated RLS test, see `security.md`).
